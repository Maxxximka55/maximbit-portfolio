CASE 02 // CODE REVIEW & BUGFIX
PR #14 Автор: Maximbit Ветка: fix/ai-bot-prod-hardening Стек: Python 3.11 + aiogram 3 + aiosqlite

Стабилизация коммерческого Telegram-бота после генерации нейросетью

Заказчик принёс бота-магазина, собранного через ИИ: бот «зависал» у всех при проверке оплаты, падал на массовой рассылке и терял заказы при перезагрузке сервера. За 3 часа устранены 4 корневые проблемы с полным сохранением логики.

Карта рисков рефакторинга (Risk Map)

Подсистема Что могло сломаться при фиксе Как закрыто и проверено
Платёжный клиент (aiohttp) Утечка открытых TCP-сокетов при создании новой ClientSession на каждый запрос Сессия создаётся один раз на старте Dispatcher и закрывается в хуке on_shutdown
База данных (SQLite → WAL) Ошибка database is locked при одновременной записи заказа и чтении каталога Включён PRAGMA journal_mode=WAL, добавлен busy_timeout=5000 и параметризация
Рассылка пользователям Бан бота по FloodWait при отправке > 30 сообщений в секунду Явный троттлинг 20 msg/sec + перехват TelegramRetryAfter с автоматической паузой
Слой запуска (systemd) Падение сервиса при обрыве сети во время старта VPS Указаны After=network-online.target и Restart=always с задержкой 5 сек

Куда смотреть в первую очередь (Attention Ranking)

  1. ПРИОРИТЕТ #1 — КРИТИЧНО

    Удаление синхронного requests.get()

    Один медленный ответ от платёжного шлюза (3–5 сек) полностью морозил event loop для всех остальных клиентов бота.

  2. ПРИОРИТЕТ #2 — БЕЗОПАСНОСТЬ

    Устранение SQL-инъекции и блокировок БД

    Подстановка данных через f-string в SQL-запрос создавала риск подмены баланса и повреждения таблицы заказов.

  3. ПРИОРИТЕТ #3 — НАДЁЖНОСТЬ

    Отказоустойчивая рассылка

    Первый же клиент, заблокировавший бота, прерывал всю рассылку — остальные 90% базы не получали оффер.

  4. ПРИОРИТЕТ #4 — ЭКСПЛУАТАЦИЯ

    Автоподнятие через systemd

    Запуск в ручной консоли умирал после разрыва SSH. Теперь бот сам поднимается за 5 секунд при любом сбое.
